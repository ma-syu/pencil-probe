## 事実

シェルで「パターン|理由」形式のルールを配列に持ち、
`${rule%%|*}` で分解すると、**パターン内の `|`（正規表現の選択）で切れる**。

```bash
rule='>[[:space:]]*[^|&]*\.(swift|sh)|リダイレクトによる上書き'
echo "${rule%%|*}"
# → >[[:space:]]*[^      ← [^| の | で切れている
```

`%%` は「最長の後方一致を削除」だが、パターンが `|*` なので
**最初の `|` 以降すべて**が削られる。

## 遭遇した経緯

2026-08-09、`scripts/hooks/pre-bash-guard.sh` の実装中。
`cat > Sources/Core/Foo.swift` をブロックすべきところ、素通りした。

負のテストを書いていたため即座に検出できた。
テストが無ければ「ガードが効いている」と誤認したまま進んでいた。

## 対処

区切りには**正規表現に現れない文字列**を使う。ここでは `@@` を採用。

```bash
rule='>[[:space:]]*[^|&]*\.(swift|sh)@@リダイレクトによる上書き'
pattern="${rule%%@@*}"
reason="${rule#*@@}"
```

同じ形式を使っていた `check-unsafe-api.sh` と
`check-purity-boundary.sh` も予防的に変換した。
これらのパターンにはたまたま `|` が無く動作していたが、
今後パターンを追加したときに同じ罠を踏む。

変換には冪等・dry-run 付きの移行スクリプトを作成し、
手作業ではなくスクリプトで実施した。

**そのスクリプトは変換完了後に削除した。**
一度きりの移行であり、新規コードは最初から `@@` で書くため
再実行の必要がない。残すと「今も必要か」を後から判断できなくなる。
必要になれば `git log --diff-filter=D -- scripts/` で復元できる。

## 派生的な教訓

**「たまたま動いている」コードは、条件が変わった瞬間に壊れる。**
このケースでは、パターンに `|` を含まない限り正しく動作していた。
1 つ選択を含むパターンを追加しただけで破綻する設計だった。

区切り文字を選ぶときは「今のデータに含まれないか」ではなく、
「**将来のデータに含まれ得るか**」で判断する。
