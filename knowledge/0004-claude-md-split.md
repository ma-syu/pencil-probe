## これは仮説である

まだプロジェクトが 1 つしか無い段階で、
「どの規約がプロジェクト非依存か」を**推測で決めた**。
2 つ目のプロジェクトができた時点で検証し、必要なら戻すこと。

断定的に書かれているが、実測の裏付けは無い。

## 分割の内容

| 置き場所 | 内容 | 行数 |
|---|---|---|
| `~/.claude/CLAUDE.md` | 文書の置き場所ルール / イテレーション手順 / コミット規律 / ファイル編集 / コード構造の閾値 / コメント方針 / 記録の方法 | 100 |
| `<project>/CLAUDE.md` | 実行環境 / できないこと / セキュリティ制約 / コード配置 / 言語の使い分け / 既知の落とし穴 | 83 |

Claude Code は両方を自動でコンテキストに載せるため、
合成や生成の仕組みは不要だった。

## 分割の根拠（すべて推測）

**共通側に置いた理由**: どのプロジェクトでも同じはずだと考えた。
イテレーション手順、コミット規律、Write 禁止、CC/関数長の閾値は
言語や環境に依存しないと判断した。

**プロジェクト側に置いた理由**: この環境固有だと考えた。
Virtual Mac、Apple Account 非対応、ブリッジ接続に起因する
セキュリティ制約、上流 PR があるための英語指定。

## 判断が微妙だったもの

- **言語の使い分け（英語/日本語）**
  上流 PR がある場合のみ必要なので、プロジェクト側にした。
  だが「上流に出すなら英語」という原則自体は汎用かもしれない。

- **セキュリティ制約**
  `0.0.0.0` 禁止はブリッジ接続だから重大だが、
  一般的にも避けるべき事項ではある。

- **CC/関数長の閾値**
  言語非依存の原則として共通側にしたが、
  プロジェクトの性質によっては緩めたい場合がある。

## 検証方法

2 つ目のプロジェクトを始めたら以下を見る。

1. 共通側の各項目が、新プロジェクトでもそのまま通用するか
2. プロジェクト側に書いた項目のうち、新プロジェクトでも書いたものはないか
   → あればそれは共通だった
3. 各プロジェクトの `./scripts/rule-audit.sh` で、
   違反される規約に偏りがあるか

## 検査

`constraints/check-docs.sh` が以下を検査する。

- 共通側の実体が存在するか（プロジェクト側が参照している場合）
- 共通側の行数（目安 120）
- 合計行数が実際にコンテキストへ載る量であることを明示

片方だけ見ても実態は分からないため、両方を検査対象にしてある。

## 派生的な論点

「実測してから決める」と「仮説を立てて検証する」は対立しない。
**変更コストと巻き戻しコストが低ければ、仮説を形にする方が速い。**

一体のままだと仮説すら存在せず、後から検証もできない。
分割という形で仮説を明示したことで、
「これは共通だと考えた」という判断が記録として残った。

ただし**仮説が仮説だと分かる形にしておくこと**が条件。
断定的に書くと、後から読む者（AI を含む）が既定事実として扱う。
両方の CLAUDE.md 冒頭に「この分割は仮説である」と明記したのはこのため。
