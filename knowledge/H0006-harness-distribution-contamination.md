## 事実 1: 配布元の汚染

`nixos-config/harness/` は検査スクリプト群の配布元。
配布元に検査を回していなかったため、ダウンロード時の同名衝突で
混入した `-2` 付きの重複ファイルに気づけなかった。
プロジェクト側にも同じ重複があり、旧版が配布されていた。

### check-stale-files.sh が検出できなかった原因

`check-stale-files.sh` は `git ls-files` で対象を列挙する。
ハーネスは `.git/info/exclude` で追跡対象から除外されているため、
検査対象に入らない。

**追跡対象外にしたことで、そこの残骸が検出されなくなる**
という除外の副作用。除外は「無視する」ではなく「見えなくする」であり、
見えない場所に問題があっても気づけない。

### 構造的な弱点

コピーによる配布方式は実体が複数箇所に存在する。
配布元が汚染されると全プロジェクトへ伝播する。

| 対策 | 種類 | 状態 |
|---|---|---|
| Nix パッケージ化（実体を 1 つにする） | 根本解決 | 予定 |
| harness を正とし、そこから一方向に配布を徹底 | 運用 | 実施中 |

## 事実 2: 「疑った側が誤っていた」が 3 度起きた

同日中に、記録や既存実装を疑って調べた結果、
疑った側（AI）の判断が誤っていたケースが 2 件あった。

### PR #163（P0002）

AI が「OpenDisplay の PR #163 は幻覚だろう」と疑った。
実際は記録の方が正しかった。
Issue #4 が Open のままだったため「未実装」と即断し、
PR 一覧・リリースノートを確認しなかった。

→ P0002 に「Issue の状態だけで実装の有無を判断しない」と記録済み。

### Package.swift

AI が「Package.swift は単一ターゲットで、check-dependency-graph.sh が
空振りしていた」と判断した。
実際は Phase 0 の時点で正しく層ごとに分割されていた。
問題は検査スクリプト側にあった:

- `target_block` が複数行定義で 1 行しか取得しなかった
- `check_dependency_direction` が層名（IO）とターゲット名（pencil-probe）を
  混同し、IO 層を丸ごとスキップしていた

→ P0005 に修正内容を記録済み。

## 事実 3: 報告と実態の乖離

同日中に、AI が実行結果を確認せずに報告した事例が 2 件あった。

- 「コミットした」と報告したが、実際には未実行だった
- 「MUST_NOT_IGNORE から外した」と述べたが、実際には残っていた

いずれも「確認せずに述べた」ことが原因。
`git diff` / `grep` / `git ls-files` で実態を確認してから報告する。

## 教訓

### 疑った結果も検証が要る

疑うこと自体は正しい。しかし**疑った結果も検証が要る**。

「AI の出力は疑うべき」という前提が強すぎると、
正しい情報まで棄却するという**逆方向の誤り**が起きる。
疑いは仮説であり、検証して初めて結論になる。

| 疑い | 実際 | 検証で判明したこと |
|---|---|---|
| PR #163 は幻覚 | 実在した | Issue の状態 ≠ 実装の状態 |
| Package.swift が未分割 | 分割済みだった | 検査スクリプト自体にバグがあった |
| Xcode .xip が小さすぎる | 正規のサイズだった | 古い記事の数値で現行版を判断した（P0007） |

### FAIL したとき、対象が悪いとは限らない

Package.swift の事例では、`check-module-boundary.sh`（自分が書いた検査）が
FAIL したことを受けて「Package.swift が悪い」と判断した。
実際は検査側の実装ミスだった。

**自分が書いた道具の出力を、道具を疑わずに信じた**という構造。
これは「PASS ≠ 機能している」の裏返しであり、
**FAIL も同様に疑うべき**という教訓になる。

特に新しく書いた検査は、まず「正しい入力で PASS するか」を
確認してから使う。`check-module-boundary.sh` は負のテスト
（違反を検出できるか）はしていたが、正のテスト
（正しい構成で PASS するか）を実プロジェクトの Package.swift で
確認していなかった。

### 報告する前に実態を確認する

AI は「やった」と報告しがちだが、実行の成否は出力で確認しなければ分からない。
報告の前に `git status` / `git diff` / `grep` で実態を検証すること。
